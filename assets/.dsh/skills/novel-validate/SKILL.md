# novel-validate

## 用户输入

```text
$ARGUMENTS
```

支持参数：
- `N` — 验证第N章
- `N,M,...` — 多章校验（如 `12,15,20`），对每章**依次**执行单章验证（含自动修复），最后汇总报告
- `all` — 全书验证（逐章执行）

## 执行步骤

### 1. 确定验证范围

- 数字参数 → 单章验证
- 逗号分隔多章（如 `12,15,20`）→ 依次对每个章号执行"单章验证 + 自动修复"，最后汇总报告
- `all` → 遍历 `novel/chapters/` 下所有已有章节
- 检查 `novel/chapters/[N]/content.md` 是否存在，不存在则报错
- 多章/全书模式：任一章出现 CRITICAL/ERROR 时，该章修复完成后再继续下一章，不中断整个流程

### 2. 执行脚本验证

🔴 **验证前先格式化（符号替换 + 段落分段），与写作命令 Step 3 后处理三件套对齐**：

```powershell
pwsh -NoProfile -File .dsh/scripts/fix-punctuation.ps1 -Chapter N
pwsh -NoProfile -File .dsh/scripts/reformat-chapter.ps1 -Chapter N
pwsh -NoProfile -File .dsh/scripts/validate-chapter.ps1 -Chapter N
```

- `fix-punctuation.ps1` — 符号替换（英文标点→中文标点，含数字上下文豁免）
- `reformat-chapter.ps1` — 段落分段（一句一段）
- 多章/全书模式：对每个章号依次执行上述三件套，再进入该章验证
- 🔴 执行 .ps1 必须使用 `pwsh -NoProfile -File`，禁止 `-Command`


验证硬指标（脚本负责）：

| # | 检测项 | 级别 | 说明 |
|---|--------|------|------|
| 1 | 章节标题 | ERROR/WARNING | 首行必须为 `# 第N章 xxx` 格式；缺失/非标题→ERROR，章节号与验证章号不一致→WARNING |
| 2 | 字数范围 | ERROR | 正文中文字符 ∈ [min, max]（不含章节标题），范围取自 `.dsh/config.yaml` 的 `wordCount` 段，缺省 [2000, 3500] |
| 3 | 风格指纹偏差 | WARNING | 与前10章固定基准相比，平均句长/对话比例/叹号频率偏差 > 阈值 |
| 4 | 格式规范 | WARNING | 段落超长(>300字) |
| 5 | 英文标点 | ERROR | 正文中不允许使用英文标点 |
| 6 | 设定冲突（脚本正则） | CRITICAL | 用 `core.md` 设定的冲突正则匹配正文（如境界数量、禁写词） |
| 7 | 伏笔ID格式 | WARNING | 旧格式伏笔ID（F-NNN）建议迁移 |
| 8 | 元数据泄漏 | ERROR | 正文中混入伏笔标记/回收标记/宪法标注/场景编号等 |
| 9 | 章节编号泄漏 | ERROR | 正文/台词中出现"第X章"等章节元数据（跳戏），须改为剧情内时间/事件锚点 |
| 10 | 波浪线标记 | ERROR | 正文中出现 `~泛称~` 设计稿标记（会渲染为删除线），须去掉波浪号直接写泛称 |
| 11 | 对话格式 | ERROR | 对话必须使用中文双引号""包裹，禁止「」『』英文引号等 |
| 12 | 结束标记 | ERROR | 禁止"（本章完）""（未完待续）"等章节结束标记 |
| 13 | 场景分隔符 | ERROR | 正文中禁止出现独占一行的纯符号分割（如 `——`、`……`、`***`、`---`、`===`、`· · ·`），场景必须叙事自然衔接 |
| 14 | 英文内容(AI) | WARNING→ERROR | 脚本列出英文单词，AI判断：专有名词/缩写（CNN、WiFi等）→ PASS；中文混入普通英文 → ERROR（步骤2.8） |
| 15 | 角色名(AI) | WARNING | AI语义判断正文中未登记角色（步骤2.5） |
| 16 | 设定一致性(AI) | CRITICAL | AI语义比对 [不可变] 规则冲突（步骤2.6） |
| 17 | 创作约束(outline头部) | WARNING→CRITICAL | AI比对 `outline.md` 头部「创作约束」中的死线 / 避毒指南 / 豁免项（步骤2.7） |
| 18 | 角色档案一致性(AI) | WARNING | 角色设定文件演化记录 / 能力 / 关系网 与 state.yaml、summary、正文三方一致（步骤2.9-14/15/16） |
| 19 | 书籍元数据一致性(AI) | WARNING | `bookinfo.md` 书名/类型/标签/简介与正文风格定位一致（步骤2.9-17/18） |
| 20 | 设计稿反向合法性(AI) | WARNING→CRITICAL | `design.md` 是否违反 outline 创作约束 / 擅自改变大纲关键事件 / 与全书走向相悖（步骤2.9-19/20/21） |
| 21 | 跨章重复/意象雷同(AI) | WARNING→CRITICAL | 相邻章节结尾/意象/钩子是否雷同，设计稿是否预埋跨章意象复用（步骤2.9-22） |

### 2.4.5 AI味专项检查（调用 humanizer-zh 技能）

🔴 **主动调用 humanizer-zh 技能**：执行 AI味相关检查（英文内容 AI 判断、文风/节奏风险、清单体/八股词/无内心流等）前，先 `use_skill humanizer-zh` 加载其去AI味规则（24种AI写作痕迹 + 快速检查清单 + 质量评分），作为判定与回修的依据清单；技能内容与验证规则并用，技能未覆盖处按本项目规则执行。

### 2.5 AI 角色名校验

🔴 **角色名检测由 AI 完成，不使用正则**（正则无法准确区分角色名与普通词语，误报率极高）。

执行：
1. 读取 `novel/constitution/characters/` 目录下所有角色文件名，得到已登记角色名列表
2. 读取 `novel/chapters/[N]/content.md` 正文
3. AI 自行理解正文语义，判断正文中实际出现了哪些**角色**（人物），逐个比对是否在已登记列表中
4. 如发现未登记角色 → 列为 WARNING

🔴 判断标准：
- 只有**真正的人物角色**才算（有名字、有对话或行动的人物）
- 代词（他/她/它）、称谓（老头/前辈/少年）、描写性词语（恭敬/沉声/轻声）**不算**角色名
- 群众性称呼（众人/弟子们/围观者）**不算**角色名

### 2.6 AI 设定一致性校验

🔴 **语义级设定冲突由 AI 完成，弥补脚本正则的不足**。

执行：
1. 读取 `novel/constitution/core.md` 中所有标记 `[不可变]` 的规则条目
2. 读取 `novel/chapters/[N]/content.md` 正文
3. AI 逐条对比：正文中是否有与任何 `[不可变]` 规则**语义冲突**的内容
4. 冲突项列为 CRITICAL

🔴 检查重点：
- 力量体系等级数量是否被突破（如"7境"变成了8境，或凭空出现新境界名称）
- 角色能力是否越级（低境界使用了高境界才能用的能力）
- 地理/历史硬设定是否被矛盾描述
- 已死亡角色是否复活出场（对比 state.yaml 中 status: dead 的角色）

🔴 注意区分：
- "扩展未定义的细节"**不算**冲突（如宪法没规定某地的气候，正文自由发挥OK）
- "违反已定义的规则"**才算**冲突（如宪法说渡劫是最高境界，正文写了更高境界）
- 不确定是否冲突 → 列为 WARNING 而非 CRITICAL，交给用户判断

### 2.7 AI 创作约束校验

🔴 **审核红线与创作避毒指南以 `novel/outline.md` 头部「创作约束」段为准，不与 `core.md` 的 `[不可变]` 规则混用。**

执行：
1. 读取 `novel/outline.md` 头部「创作约束」段
2. 读取 `novel/chapters/[N]/content.md` 正文
3. AI 逐条比对：正文是否触犯「死线」或本书明确禁写项；是否对「黄线 / 弹性区 / 豁免项」处理失当
4. 结果分级：
   - 触犯死线 / 明确违反本书禁写项 → `CRITICAL`
   - 黄线 / 弹性区写法过满、缺少技巧处理、与豁免项不一致 → `WARNING`

### 2.8 AI 英文内容校验

🔴 **英文内容判断由 AI 完成，脚本仅列出检测到的英文单词**（脚本无法区分专有名词与错误混入）。

执行：
1. 读取脚本验证结果中"英文内容"项列出的英文单词列表
2. AI 逐词判断每个英文单词是否属于以下**合理使用**情况：
   - 专有名词/品牌名（如 CNN、NBA、iPhone）
   - 通用缩写（如 WiFi、GPS、DNA、GBU）
   - 技术术语/型号（如 AK47、T-72）
   - 小说世界观中的设定名称
3. 不属于上述情况的英文单词 → 列为 ERROR（如"他very开心"中的"very"）

🔴 判断标准：
- 该英文词在中文语境中是否有约定俗成的使用习惯 → 合理
- 该英文词是否可以且应该用中文替代 → ERROR
- 不确定 → 列为 WARNING，交给用户判断

### 2.9 AI 连续性校验 + summary/state 漂移检查（SubAgent `continuity-validator`）

🔴 **一次性完成正文连续性校验 + summary/state 漂移检查**，使用 `stage=chapter-full` 模式合并原 2.9 + 2.10。

**a) 检查并补齐 summary.md**
- 检查 `novel/chapters/[N]/summary.md` 是否存在：
  - 不存在 → 调用 SubAgent `chapter-summarizer` 生成摘要（传入章节号 N），等待完成
  - 存在 → 继续

**b) 角色谱系统计（脚本先行，零 token）**

🔴 **新角色引入节奏 / 角色谱系平衡两项，量化统计由脚本直接从设计稿提取角色完成，AI 无需逐字读正文**。

主流程先跑一次脚本作为**提前预警**（校验脚本可用性 + 快速给出量级参考）：

```powershell
pwsh -NoProfile -File .dsh/scripts/analyze-roster.ps1 -Chapter N
```

脚本扫描 N-10 ~ N 章 `design.md` 场景表格的"出场角色"列，输出：
- `activeNamedTotal` — 近10章活跃命名角色总量（建议 ≤25）
- `sceneOverload` — 单场命名角色 >5 的场景清单
- `newCharsThisChapter` — 本章新引入角色
- `staleCores` — 出场 ≥4 次但最近 5 章未再登场的核心配角
- `roster` — 各角色出场章节数 / 首次 / 最后出场

🔴 **判定责任在 SubAgent**：`continuity-validator` 会在其 `<context_loading>` 阶段**自行再次执行同一脚本**获取量化数据，作为检查项 7/8 的正式判定依据。主流程此处的运行结果仅用于提前预警/发现问题，**不作为 AI 判定的唯一来源**——即使主流程这里失败或遗漏，validator 自跑脚本也能独立闭环，第 7/8 项不再出现"未验证项"缺口。

**c) 调用连续性校验**

调用 SubAgent `continuity-validator`，使用 `stage=chapter-full`，一次性检查：

🔴 **三方一致性校验（outline ↔ design ↔ content）：**
1. **设计稿兑现度**：`design.md` 的关键动作、关键结果、章节钩子是否在 `content.md` 中全部兑现；场景被整段跳过 → CRITICAL
2. **大纲完成度（端到端闭环）**：从 `outline.md` 提取本章事件/目标，直接与 `content.md` 比对，防止"设计稿漏了A → 正文也漏了A"的穿透性遗漏；大纲事件完全未体现 → CRITICAL
3. **偏离预警**：正文出现大纲和设计稿中都没有的重大事件（新增主线转折、新增重要角色登场等）→ WARNING

**常规连续性检查：**
4. 时间线是否与上一章正文、近章摘要、`state.yaml`、`outline.md` 衔接
5. 数值 / 资源 / 资产是否有来源、消耗、余额闭环（如本书有这类系统）
6. 角色状态是否前后一致（位置 / 伤势 / 知情范围等）
7. 伏笔是否真的回收，新钩子是否成立
8. **新角色引入节奏（仅 WARNING，量化依据 = analyze-roster.ps1 输出）**：基于 `newCharsThisChapter`（本章新引入角色）与 `sceneOverload`（单场 >5）判断是否过密；基于 roster 出场章节判断是否连续多章无新角色、贯穿配角是否每章都出场；结合设计稿判断"本章戏份少但后续会复用的角色"是否被错误压成匿名背景
9. **角色谱系平衡（仅 WARNING，量化依据 = analyze-roster.ps1 输出）**：基于 `activeNamedTotal`（近10章活跃命名角色总量 >25 预警膨胀）；基于 `staleCores`（核心配角放长假）判断关系网断裂；基于新老角色出场分布判断新角色是否挤占老角色戏份
10. **文风 / 节奏风险（仅 WARNING）**：如连续大段对话无动作承接、场景推进过平、章末钩子偏弱等

**summary/state 漂移检查（原 2.10）：**
11. summary 是否漏掉重大结果
12. state 是否把正文里未发生的未来状态提前写进来
13. 关键资产与角色状态是否正确更新

**角色档案一致性（本章出场角色）**：
14. `characters/[角色].md` 的「演化记录」是否与 `state.yaml` / `summary.md` / 正文三方一致
15. 角色设定文件的「能力 / 关系网 / 状态 / 位置」字段是否与正文实际呈现矛盾
16. 正文出现角色重要变化（升级/受伤/物品增减/关系变化）时，是否已在演化记录或 state 中反映（遗漏 → WARNING）

**书籍元数据一致性（bookinfo ↔ 正文）**：
17. `bookinfo.md` 的书名 / 类型 / 标签 / 简介基调 与正文实际风格是否一致（如"历史脑洞长生流"写成现代都市日常 → WARNING）
18. 正文是否出现与书籍定位严重冲突的写法（换题材、变画风等 → WARNING）

**设计稿反向合法性（design ↔ outline 约束，design / chapter-full 模式重点）**：
19. `design.md` 是否违反 `outline.md` 头部「创作约束」段（死线 / 避毒指南 / 豁免项）
20. `design.md` 是否擅自改变大纲设定的关键事件走向 / 角色命运（严重偏离 → WARNING）
21. `design.md` 的场景设计是否与本书卷目标、全书走向相悖

**跨章重复 / 意象雷同（相邻章节对比）**：
22. 本章结尾与上一章（或近2~3章）结尾是否用相同/近似的收束意象或句式（如"等下一场戏的开锣声"→"来接下一场的开锣声"）→ 完全复制 → CRITICAL；近似复用 → WARNING
23. 整章是否反复使用与近章相同的比喻系统（戏台/开锣/翻页/排队等专属意象连续多章复用）→ WARNING
24. `design.md` 是否出现"与第N章结尾形成跨章呼应"之类的指令，或写死与近章相同的修辞意象 → WARNING（设计稿不应指定具体意象复用）
25. 连续多章章末钩子类型单一（都是"XX来了"式悬念）→ WARNING
    🔴 区分：真·剧情伏笔回响（约定信物、重复物品）不算雷同——那是蓄意设计；只有修辞/收束方式/意象比喻的复制才算

**d) 结果处理**

🔴 **主会话须独立核验 `continuity-validator` 各项评定是否正确**（对照正文 / summary / state 实际内容复核），不得盲信子会话结论——误报可驳回并记录理由，漏报须补入验证报告；仅在核验确认为真问题后，才按下述规则修复。

- **CRITICAL / WARNING** → 统一走同一闭环（不限次数，直到 validator 评定 PASS 或主会话核验后认为属于误报）：
  - summary 漏写/错写 → 主会话直接修正 `summary.md`（补漏项/改错项，最小改动） → 重跑 `validate-summary.ps1` → `sync-state.ps1` → 再次调用 `continuity-validator (chapter-full)`
  - state.yaml 偏移 → 重跑 `sync-state.ps1`（从 summary 重新解析） → 再次调用 `continuity-validator (chapter-full)`
  - 正文问题 → 主会话直接最小回修（见步骤4） → 再次调用 `continuity-validator (chapter-full)`
- **PASS** → 继续

### 4. 自动修复（默认执行，无需 --fix）

🔴 **验证发现任何 CRITICAL / ERROR / WARNING 后默认自动修复，无需任何参数开关**。修复由**主会话直接完成**，不再回调 SubAgent `novel-writer`。校验报告已给出具体问题行 + 最小修复建议，主会话直接读取相关文件、只改必要位置（最小回修，禁止整章重写）：

- CRITICAL / ERROR / WARNING → 主会话对照验证报告中的问题清单，直接修正对应文件（正文 `content.md` 字数不足则扩写已有场景，超出则精简冗余描写；summary / state 问题按步骤2.9d 分类自愈；均以最小回修为原则）
- 修复路由为 `manual-review` → 直接提示人工介入，不自动修改

🔴 修复后**自动**重新执行步骤 2~2.9 全部验证（含 continuity-validator (chapter-full) 重跑），循环直到 validator 评定 PASS（无 CRITICAL / ERROR / WARNING）或主会话核验后认为属于误报，不再要求用户手动确认每次修改。修复后复验同样先跑 fix-punctuation + reformat（步骤2三件套）再 validate。

🔴 **多章模式（`N,M,...`）**：对每个章号依次执行"验证 → 自动修复 → 复验通过"后再进入下一章；每章结果单独记录，最后统一汇总报告。

## 约束
